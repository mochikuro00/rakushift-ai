## 📌 このマニュアルについて

**ラクシフトAI** を日常運用するために必要な操作を、  
**手順通りにやれば誰でもできる** ように書いています。

---

## 🏗️ システム全体像（5秒で理解）

```
お客さん（ブラウザ）
    ↓ アクセス
[Cloudflare Pages] ← HTMLとJavaScriptを配信するサーバー
    ↓ データ取得
[Supabase] ← データベース（スタッフ情報、シフトデータ等）
    ↓ シフト生成
[Railway] ← AIがシフトを計算するサーバー（Python）
    ↓ 決済
[Stripe] ← クレジットカード決済
```

**つまり：**
- **Cloudflare Pages** = ホームページを置く場所
- **Supabase** = データを保存する場所
- **Railway** = AIが計算する場所
- **Stripe** = お金を受け取る場所

## 📋 日常業務

### 1. 新しいお客さんが契約したとき

**自動でこうなります：**
```
お客さんがStripeで決済
  ↓ 自動
テナント（契約ID）が自動作成される
  ↓ 自動
メールアドレスが登録されていれば案内メールが自動送信
```

**あなたがやること：**
1. 管理画面 (admin.html) にログイン
2. 「テナント一覧」で新規テナントを確認
3. もしメールが届いていなければ「案内送信」ボタンでメール再送

---

### 2. お客さんからパスワードを忘れたと言われたとき

**答え：** マスターパスワード `rakushift1234` でログインしてもらう

**その後：**
1. お客さんにログインしてもらう
2. 「設定」→「パスワード変更」で新しいパスワードを設定してもらう

---

### 3. お客さんのプランを変更したいとき

**お客さん自身で変更できます：**
1. ログイン後、サイドバーの「プラン管理」をクリック
2. 「プラン変更」ボタン → Stripeのポータルに移動
3. 新しいプランを選択 → 決済 → 自動反映

---

### 4. お客さんの決済が失敗したとき

**自動でこうなります：**
```
決済失敗
  ↓ 自動
画面にオレンジの警告バナーが表示される
「お支払いに問題があります」
  ↓ 21日間放置
自動でライセンス停止
  ↓ 6ヶ月後
手動でデータ削除（管理画面から）
```

**あなたがやること：** 基本的に何もしなくてOK（全自動）

## ⚠️ 店舗情報・スタッフ設定の重要性

お客様（店長）に対しては、必ず**「設定の正確さがAIの精度を100%決める」**ということを伝えてください。

### 🟢 正確に設定した場合（理想）
- **設定内容**: 
  - 店舗情報：営業時間、時間帯別の必要人数、**店舗独自のポジション（ホール・キッチン・受付など）**、管理者の必須カバーなどを正確に入力。
  - スタッフ：NGペア・必須ペア、**週の最低出勤日数**、**希望時間の考慮トグル（バイトはON、社員はOFF）**、役職、担当ポジションを正確に入力。
- **AIの動き**: 「特定の人が連日出勤しない」「ピーク時はベテランを配置する」「稼ぎたい人を優先して入れる」「休みたい日には入れない」といった、**店長顔負けの完璧なパズル**を解き明かし、誰もが納得するシフトを全自動で生成します。

### 🔴 設定が甘い場合（失敗例）
- **設定内容**:
  - 店舗情報：必要人数をすべて0にする、管理者のカバー条件をオフにする。
  - スタッフ：NG日だけ入力して、役職や希望時間、人間関係を白紙にする。
- **AIの動き**: AIは「制限がない（誰をどこに入れても良い）」と判断します。その結果、「同じ人が5連勤する」「遅番の翌日に早番になる」「新人だけで店を回す」など、**法律上はエラーではないが、人間から見ると実用的でない（使えない）シフト**が出来上がります。

> **お客様への案内トーク例**:  
> 「AIは入力された条件を『絶対に守るべき法律』として学習します。最初は少し手間かもしれませんが、スタッフの希望や店舗のルールを細かく入力すればするほど、AIは圧倒的に賢くなり、毎月のシフト作成が1クリックで終わるようになります！」

## 🤖 AIシフト生成の仕組み（かんたん版）

```
① お客さんが「AIシフト作成」ボタンを押す
  ↓
② まず人が足りているかチェック（/check API）
  ↓
③ 足りていたら → AIがシフトを計算（/generate API）
   足りていなかったら → 「人員不足です」と警告表示
  ↓
④ 計算結果をプレビュー画面で表示
   ※【重要】赤斜線の太枠になっているシフトは「イレギュラーシフト」です。店舗の人手不足によりAIがやむを得ず割り当てた箇所ですので、必ず店長が目視で確認し、手動で修正してください。
  ↓
⑤ お客さんが「確定して保存」を押したらDBに保存
   「キャンセル」を押したら破棄
```

**AIが守るルール（優先度順）：**

| 優先度 | ルール | 緩和できる？ |
|-------|--------|-----------|
| 🔴 絶対 | 1日8時間以内、週40時間以内 | ❌ できない |
| 🔴 絶対 | 6h超→45分休憩、8h超→60分休憩 | ❌ できない |
| 🔴 絶対 | 連続6日まで、週1日は休み | ❌ できない |
| 🔴 絶対 | 希望休には絶対入れない | ❌ できない |
| 🔴 絶対 | 最低出勤日数（設定時） | ❌ できない |
| 🟡 努力 | 人員配置（最低○名） | ⚠️ 人不足時は緩和 |
| 🟡 努力 | 管理者が常にいること | ⚠️ 人不足時は緩和 |
| 🟢 最適化 | スタッフ間の公平性 | ✅ できる |
| 🟢 最適化 | 人件費の最小化 | ✅ できる |

## ⚠️ やってはいけないこと

1. **`js/config.js` をGitHubに公開しない**（Supabase Anon Keyが入っている）
2. **`platform_settings` テーブルを直接編集しない**（Stripeキー等が壊れる）
3. **テナントを手動で直接DBから削除しない**（関連データが残る → `delete_tenant_data` RPCを使う）
4. **Railwayの環境変数 `SUPABASE_SERVICE_KEY` を外部に漏らさない**

## 📞 緊急時の対応

| 状況 | 対応 |
|------|------|
| サイトが完全に落ちた | Cloudflare → Railway → Supabase の順に確認 |
| 決済が止まった | Stripeダッシュボードでイベントログを確認 |
| データが消えた | Supabaseのバックアップから復元（自動バックアップあり） |
| 不正アクセスの疑い | Railwayログを確認、必要に応じてCORS制限を強化 |
