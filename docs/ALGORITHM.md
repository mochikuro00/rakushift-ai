# ラクシフトAI シフト生成アルゴリズム仕様書

対象コード: [python/scheduler.py](../python/scheduler.py) / エンドポイント [python/main.py](../python/main.py) `/generate`

数理最適化 (MILP) を主軸に、失敗時はグリーディ法でフォールバックする多段アルゴリズム。
「絶対に守る制約 (ハード)」と「なるべく満たす制約 (ソフト=ペナルティ最小化)」を分離している。

---

## 1. 入力

| 入力 | 内容 |
|---|---|
| `staff_list` | スタッフ配列 (給与形態・役職・週/月の最低/最大日数・連勤上限・最大労働時間・NG曜日/日付・eligible_patterns 等) |
| `config` | 営業時間・定休日・`custom_shifts`(シフトパターン)・`staff_req`(必要人数)・`time_staff_req`(時間帯別増員)・`allow_overstaffing`・`break_rules` |
| `dates` | 生成対象の日付配列 |
| `requests` | 承認済み出勤希望/休み希望 |
| `existing_shifts` | 固定する既存シフト (空きだけ埋めるモード用) |

`custom_shifts` の各パターンは `name/start/end/count_weekday/count_weekend/count_holiday` と、
本機能の **`force_rest_next_day`** (翌日強制休み=夜勤2連勤防止) を持つ。

---

## 2. 前処理 (`__init__`)

1. 不正スタッフ/不正日付を除去
2. **シフトパターン構築**: `custom_shifts` を読み、各パターンに `force_rest_next_day` を引き継ぐ
3. **営業日リスト** `_operational_dates`: 定休日を除いた日付。連勤判定は「休業日を挟んでも実出勤を連続カウント」するためこの営業日ベースで行う
4. 必要人数 (`min_weekday/weekend/holiday/manager`)、時間帯別増員 (`time_staff_req`)、休憩ルール、過剰配置可否を確定

---

## 3. シフト候補生成 (`_build_shift_options`)

スタッフ×日付ごとに、配置可能な「シフトの選択肢(option)」を列挙する。

- 各シフトパターンの開始/終了をそのまま採用 (営業時間でクランプしない)
- 実労働時間が `max_hours_day` を超える場合は、開始固定で終了短縮 / 終了固定で開始遅延の短縮版を生成
- 休憩 > 拘束時間 となる不正候補は除外
- (start,end) で重複排除。**`force_rest` フラグ**は元パターンの `force_rest_next_day` から付与し、同一時刻が複数パターン由来なら OR 結合
- 各 option: `{start,end,start_min,end_min,hours,work_hours,is_pref,force_rest}`

---

## 4. メインフロー (`solve`)

```
n_staff, n_days から開始Tierを自動決定 (大規模ほど低Tierから = タイムアウト回避)
  staff>=150 → Tier1開始 / staff>=100 → Tier2開始 / それ以外 → Tier3開始

for tier in (start_tier .. 1):          # 3 → 2 → 1
    use_force = (tier == 1)              # Tier1 は法令以外を緩和
    result = _solve_milp(force=use_force, tier=tier)
    if result: return result
return _solve_greedy()                   # 全MILP失敗時

（_solve_milp 内、過剰配置ON時のみ）解の後に最低出勤日数を補完
```

- **Tier 3**: 品質最適化まで (希望尊重・公平性・社員優先)
- **Tier 2**: カバレッジ重視 (必要人数・パターン人数)
- **Tier 1 (force)**: 法令・物理制約のみ確実に守り、他は緩和
- 上位Tierが解けなければ下位へ降格。全滅でグリーディ

---

## 5. MILP モデル (`_solve_milp`)

### 5.1 決定変数
`x[(staff, date, option_index)] ∈ {0,1}` … そのスタッフがその日にその option で出勤するなら1。
NG日・定休日は変数を作らない。

### 5.2 目的関数
`minimize Σ(ペナルティ重み × スラック変数) − Σ(ボーナス)`
重み階層 (`class W`):

| 階層 | 重み | 例 |
|---|---|---|
| Tier1 絶対 | 100M | 必要人数不足・日次/スロット過剰 |
| Tier2 必須 | 10M | 任意スロット0名・開け閉め社員不在 |
| Tier3 重要 | 1M〜3M | 希望時間一致(−3M ボーナス)・ポジション不足・OJTメンター不在 |
| Tier4 推奨 | 50k〜500k | 希望日配置(−500k)・全員最低出勤保証 |
| Tier5 微調整 | 1k〜100k | シフト追加抑制(過剰回避)・公平性偏差・優先度/契約ボーナス |

### 5.3 ハード制約 (TIER 1 — 物理・法定、必ず充足)
1. **1日1シフト**: `Σ_oi x[s,d,oi] ≤ 1`
2. **月の最大出勤日数** 上限
3. **週の最低出勤日数** (全週・絶対遵守)
4. **月の最低出勤日数** (月給スタッフはハード / 時給はソフト1M)
5. **連続勤務上限** (営業日ベース): `max_consec+1` 連続営業日の出勤合計 ≤ `max_consec`
6. **勤務間インターバル 10時間**: 前日退勤→翌日出勤が10h未満になる option 同士は同時選択不可 `x[d1,oi1]+x[d2,oi2] ≤ 1`
7. **🌙 翌日強制休み (force_rest / 夜勤2連勤防止)** ← 本機能
   隣接カレンダー2日 (d, d+1) について
   ```
   for 夜勤option oi1 (force_rest=True) on d:
     for 全option oi2 on d+1:
       x[s,d,oi1] + x[s,d+1,oi2] ≤ 1
   ```
   **全Tier(3/2/1)で常時追加** されるため、過剰配置等のソフト目的より必ず優先される。

> max_hours 超過はハードにせず、1時間あたり 100k のソフトペナルティ (人手不足回避を優先)。

### 5.4 ソフト制約 (TIER 2 — カバレッジ)
- **日次出勤人数**: 必要人数ぴったりに収束 (不足=COVERAGE_UNDER 100M / 過剰=COVERAGE_OVER 100M、過剰配置ON時はスロット過剰を1Mに緩和)
- **15分スロット人員**: 不足/過剰をスラックで管理
- **シフトパターン別必要人数** (平日/土曜/日祝の `count_*`)
- **シフトパターン別 管理者人数** (`manager_count`): 当該パターンに入る管理者(店長/リーダー)数 ≥ 指定数 (10M)。旧「最低管理者数(常時1名)」「開け閉め社員常駐」の代替。管理者の配置はこの制約のみで制御する
- **スタッフ別パターン月間 最低/最高回数** (Tier4)
- ~~開け閉め社員常駐~~ : v3.7.179 で**廃止**。管理者配置は `manager_count` のみで制御
- **遅番優先配置** (閉店前カバー)

### 5.5 品質最適化 (TIER 3)
- **OJT制約**: 新人の時間帯にメンターが重なるよう配置
- **優先度/契約ボーナス**: shift_priority・regular契約・メンターペア
- **公平性**: スタッフ間の出勤偏差を最小化 (FAIRNESS_DRIFT)
- **希望シフト**: 完全一致−3M / ±1時間−1.5M / 希望日−500k のボーナス

### 5.6 希望・既存シフトの扱い
- **承認済み出勤希望**: 一致 option に −10M の必達ボーナス (実質固定)
- **既存シフト固定 (empty_only)**: 既存を固定変数化し、空きスロットのみ最適化

### 5.7 解の抽出
`pulp.value(x) > 0.5` の option を採用しシフト化。status が Optimal / Not Solved を採用 (それ以外は当該Tier失敗→降格)。

---

## 6. 過剰配置ON時の最低日数補完 (`_fill_to_min_days_random`)

MILP解の後、`allow_overstaffing=True` のときだけ実行。min_days 未達スタッフへ営業日をランダム追加。
**翌休を厳守するためのチェックを内蔵**:

```
fr_pat_keys = force_rest パターンの時刻集合
各スタッフ: fr_dates = 既存シフトのうち force_rest パターンに入っている日付

候補日 d を追加する前に:
  R1) 前日(d-1)が fr_dates にある → 追加しない (夜勤の翌日)
  R2) 追加optionが夜勤(force_rest)で、翌日(d+1)が既に勤務 → 採用しない
      (非夜勤の代替optionがあればそれを採用)
追加のたびに already / fr_dates を更新 (追加順に依存せず破綻しない)
```
※ NG曜日・週最大日数・連勤上限・パターン時刻一致も併せて尊重。

---

## 7. グリーディ法 (`_solve_greedy` — フォールバック)

MILPが全Tier失敗したときのみ。日付順に貪欲配置:

1. 承認済み出勤希望を先に固定 (連勤上限・**翌休ブロック**を尊重)
2. 各営業日: 管理者を先に確保 → 不足スロットを評価順(月給>メンター>評価ランク)で充足
3. 週最低出勤日数の後処理補完
4. すべての配置経路で次を尊重: NG日・連勤上限・10hインターバル・週/月日数・**翌休**

**翌休の実装**: `rest_block = {staff: 休みにすべき日}`。
force_rest option を配置したら翌カレンダー日を `rest_block` に登録し、以降その日には一切配置しない (全配置経路でチェック)。

---

## 8. 検証 (`_validate`)
生成後、必要人数±1の充足率・連勤・各種制約をログ集計し、`report` (coverage_gaps / overtime 等) を返す。

---

## 9. 翌休の最終ガード (`_enforce_force_rest_output`) — 絶対保証
`solve` が返す直前に、生成経路によらず出力を走査し、force_rest パターンに入った
翌カレンダー日の同一スタッフのシフトを**除去**する。スタッフごとに日付順で処理し、
連続夜勤も解消 (夜勤を残し翌日側を落とす)。
**強行(force)モード・過剰配置補完・グリーディ等いかなる経路でも、最終的に必ず翌休が守られる。**

## 10. 「夜勤が2日連続しない」が保証される理由 (まとめ)
- 夜勤(force_rest)に入った翌日は**全シフト禁止**(ハード制約) → 翌日の夜勤も日勤も不可
- 加えて10hインターバルでも夜勤→翌朝勤務を二重に防止
- MILP・グリーディ・過剰配置補完の**全経路**で翌休を尊重
- ハード制約のため、過剰配置などソフト目的より**常に優先**される
- 最後に §9 の最終ガードで出力を二重チェック (強行モードでも絶対遵守)
