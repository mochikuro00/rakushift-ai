## 1. 基本: ログインと画面構成

### 1.1 ログイン

URL: `https://<deploy-domain>/admin.html`

| 項目 | 値 |
|---|---|
| ログインID | `admin` (運営マスターアカウント) または運営者本部のlogin_id |
| パスワード | 初回 `rakushift1234` (※必ず変更してください) |

> ⚠️ **マスターパスワード**: `rakushift1234` は緊急復旧用フォールバックです。新規顧客テナントの初期パスワードでもあるため、本番運用ではテナント発行直後に各テナント側で変更させてください。

### 1.2 上部タブ構成

ログイン後の画面は以下6タブで構成されます。

| タブ | アイコン | 主な操作 |
|---|---|---|
| **テナント管理** | 🏢 | 顧客テナントの発行・一覧・ライセンス操作・APIキー設定 |
| **事業収益** | 📈 | MRR・ARR・Churn・LTV・新規/解約推移 |
| **紹介者管理** | 👥 | 代理店アカウント発行・報酬率設定 |
| **お知らせ管理** | 📢 | 全テナントログイン画面に表示するお知らせ作成 |
| **お問い合わせ** | ✉️ | 公開サイトからの問い合わせ受信箱 |
| **本部管理** | 🏘️ | 顧客企業ごとの本部アカウント発行 (※後述・重要) |

### 1.3 上部統計カード (常時表示)

- **総テナント** / **アクティブ** / **停止中** / **削除予定** / **月間売上 (税別)**
- すべて Supabase の `list_tenants` RPC からリアルタイム算出

## 2. テナント発行 (新規顧客の登録)

### 2.1 操作手順

1. **テナント管理タブ** を開く
2. 右上の **「+ 新規テナント」** ボタンをクリック
3. モーダルで以下を入力:

#### プラン選択
| プラン | 月額(税別) | スタッフ上限 | 備考 |
|---|---|---|---|
| Standard | ¥3,380 | 10名 | Stripe連動 |
| Pro (デフォルト) | ¥4,880 | 50名 | Stripe連動 |
| Premium | ¥9,980 | 無制限 | Stripe連動 |
| OEM代理店 | ¥4,000 | — | **Stripe非連動・手動管理**・紹介料¥3,200/件 |

#### 事業者情報 (必須)
- 組織名 / 住所 / 代表電話

#### 担当者情報 (必須)
- 担当者名 / メールアドレス / 担当者電話 (※「代表と同じ」ボタンあり)

#### 紹介者 (任意)
- 紹介者コード (既存リストからサジェスト or 新規入力可)

4. **「テナント作成」** ボタンで実行

### 2.2 自動で起こること

- **契約ID** が15桁ランダム数字で自動生成 (例: `254995332101138`)
- 初期パスワードは `rakushift1234`
- `organizations` テーブルに organization_id (UUID) が作成され、各種マスタが空状態で初期化
- `config_safe` view にメタ情報 (会社名・住所等) が保存
- ライセンスは `active` 状態で開始

### 2.3 顧客への案内

テナント作成後、テナント一覧の **「案内送信」** ボタンでログイン情報をメール送信できます (SMTP設定済の場合)。または以下を手動で伝えてください:

```
ご契約ID: 254995332101138
ログインURL: https://<deploy-domain>/index.html
初期パスワード: rakushift1234
　→ 初回ログイン後に必ず「店舗設定」から変更してください
```

## 3. テナント管理 (一覧・編集・ライセンス操作)

### 3.1 一覧テーブル

| 列 | 内容 |
|---|---|
| 組織名 / 契約ID | クリックで詳細 |
| 状態 | 🟢 アクティブ / 🟡 停止中 / 🔴 削除予定 |
| プラン | Standard / Pro / Premium / OEM |
| 担当者・メール・電話 | 連絡用 |
| 紹介者 | 紐づく紹介者コード |
| スタッフ | 現在登録されている staff 数 |
| 登録日 | 契約開始日 |
| **操作** | 👁 観覧 / 📧 案内送信 / ⏸ 停止 / ▶ 復活 / 🗑 削除 |

### 3.2 検索・フィルタ

- **キーワード**: 契約ID・組織名・紹介者コードで部分一致
- **状態**: すべて / アクティブ / 停止中
- **紹介者**: すべて / 紹介者なし / 特定紹介者

下部の「💀 削除予定経過テナント」セクションで、ライセンス停止から6ヶ月経過した物理削除対象を表示。「更新」ボタンで再取得 → 削除実行が可能です。

## 4. 本部テナント発行 — 重要 (あとから追加した機能)

> **本機能はチェーン店・FC本部・複数店舗を持つ顧客企業向けに後から追加されました。**
> 本部アカウントは「複数の通常テナント (店舗) を横断的に観覧・管理する」役割を持ちます。

### 4.1 本部アカウントとは

通常テナント (店舗) とは別レイヤーの **観覧専用アカウント** です。
1つの本部アカウントが複数の店舗テナントを「管轄」として持ち、店舗の中身を観覧できます。

### 4.2 種別 (2種類)

| 種別 | バッジ | 管轄範囲 | 用途 |
|---|---|---|---|
| **グローバル (運営者)** | 🟣 紫 | **全テナント自動的に含む** | ラクシフトAI 運営者が全店舗を横断確認する用 |
| **顧客本部** | 🔵 青 | **scope_org_ids で個別指定** | チェーン店本部が自社店舗のみ観覧する用 |

### 4.3 本部アカウント発行手順

1. **本部管理タブ** を開く
2. 右上の **「+ 本部アカウント発行」** をクリック
3. モーダルで以下を入力:

| 項目 | 必須 | 例 | 制約 |
|---|---|---|---|
| ログインID | ✅ | `hq_company_a` | 半角英数字/_/- 3文字以上 |
| パスワード | ✅ | (自動生成推奨) | 8文字以上・自動生成ボタンあり |
| 会社名 | 任意 | 株式会社○○ホールディングス | |
| 担当者メール | 任意 | hq@example.com | |
| **管轄する店舗** | ✅ | 複数選択 | 1つも選ばないと「管轄なし」(警告あり) |

4. **「発行する」** ボタンで作成完了

### 4.4 本部観覧の仕組み

#### 本部側のログイン
- 本部アカウントは `index.html` で通常のログイン画面から `hq_login` RPC 経由でログイン
- ログイン後、自分の管轄店舗の一覧が表示される

#### 個別テナントを観覧する流れ
1. 運営者が `admin.html` → 本部管理タブ → 該当本部の行を展開
2. 「管轄テナント一覧」の各店舗右の **👁** ボタンをクリック
3. `index.html?as_hq=<contract_id>` で別タブが開く → **本部観覧モード**
4. シフト表・スタッフ・店舗設定をすべて閲覧可能 (編集はサーバ遮断)

### 4.5 管轄店舗の追加方法 (2通り)

#### 方法A: 一覧から選択 (推奨)
- 本部行の **「✏️ 管轄を一覧から選択」** ボタン → 全テナントのチェックリストから複数選択 → 保存

#### 方法B: 店舗ID + 管理者パスワードで登録
> チェーン店本部側で店舗パスワードを把握している場合のセルフ登録フロー。

- 本部行の **「+ 店舗登録」** ボタン (黄色オレンジ) をクリック
- モーダルで:
  - **店舗ID** (15桁の数字)
  - **管理者パスワード** (店舗側のパスワード、または運営マスター `rakushift1234`)
- 「登録する」 → `register_store_to_hq` RPC で認証成功時に scope に追加

### 4.6 本部アカウントの削除

- 本部行の **🗑 削除** ボタン (赤)
- グローバル本部は削除不可 (運営者本人のため)
- 削除しても管轄店舗 (テナント) 自体には影響なし

### 4.7 本部アカウントの編集

| 操作 | ボタン |
|---|---|
| 管轄店舗の追加/削除 | ✏️ ペンアイコン (黄色) |
| 店舗の追加登録 | ＋ サークル (黄→橙グラデーション) |
| 削除 | 🗑 ゴミ箱 (赤) |

### 4.8 注意点

- **管轄なし** 状態の本部はログイン後「店舗が見えない」状態になります → 警告ダイアログが出ます
- **scope_org_ids は配列管理** → DB 直接編集は推奨しません (RLS バイパス機能あり)
- **観覧モードでの編集は不可** → サーバ側 (RLS / SECURITY INVOKER view) でも遮断
- 本部アカウントは **Stripe決済とは無関係** (課金は管轄テナント側で発生)

## 5. ライセンス発行・停止・復活・削除

### 5.1 状態遷移図

```
[作成] → 🟢 active
            ↓ (suspend_license)
         🟡 suspended ←→ 🟢 active  (activate_license)
            ↓ (6ヶ月経過)
         🔴 削除予定 (data_deletion_scheduled_at < now)
            ↓ (delete_tenant_data)
         💀 物理削除
```

### 5.2 ライセンス停止 (⏸)

**いつ使う**: 解約・支払い停止・トラブル発生時

1. テナント行の **⏸ 停止** ボタン
2. 確認モーダルで備考 (任意・理由を記入推奨) を入れて「確認」
3. → テナントはログイン不可になるが、**データは6ヶ月保持** されいつでも復活可能

### 5.3 ライセンス復活 (▶)

**いつ使う**: 支払い再開・誤停止からの復旧

1. テナント行の **▶ 復活** ボタン
2. 備考を記入して「確認」
3. → すぐにログイン可能・データはすべて保持されています

### 5.4 完全削除 (🗑)

**いつ使う**: 6ヶ月経過後の最終削除・GDPR削除依頼

1. テナント行の **🗑 削除** ボタン (赤)
2. ⚠️ 確認モーダル: **「この操作は取り消せません」**
3. 「確認」で `delete_tenant_data` RPC が実行され、shifts/staff/config 全データを物理削除

### 5.5 OEMプランの手動ライセンス管理

OEMプランは Stripe 非連動です。期限管理は運営側で手動運用してください:
- 月初に該当テナントの請求書発行 (社内システム)
- 入金確認後、明示的に何もしない (= active 維持)
- 未入金時は手動で「停止」操作

## 6. お知らせ管理 (全テナント向け配信)

### 6.1 お知らせの表示場所

作成したお知らせは以下に自動表示されます:

- **ログイン前画面** (`index.html` の未ログイン状態) — 上部バナー
- **ログイン後画面** (`index.html` のダッシュボード) — 上部バナー
- **本部観覧モード** — 同じバナー表示
- **運営管理画面** — 表示なし (運営者向けは別途実装)

### 6.2 新規お知らせ作成

1. **お知らせ管理タブ** を開く
2. 右上の **「+ 新規お知らせ作成」** ボタン
3. モーダルで以下を入力:

| 項目 | 必須 | 説明 |
|---|---|---|
| **タイトル** | ✅ | バナーに大きく表示される見出し |
| **本文** | ✅ | バナーに表示される詳細 (改行可) |
| **タイプ** | | ℹ️ お知らせ / 🎁 キャンペーン / 🚀 アップデート / ⚠️ 注意 (色とアイコンが変わる) |
| **優先度** | | 0〜100。高いほど上位表示。複数あるときの並び順 |
| **遷移先URL** | 任意 | 詳細ページ・LP・ヘルプ等のリンク |
| **ボタンテキスト** | 任意 | URL設定時に表示 (例: 「詳しく見る」) |
| **有効期限** | 任意 | 設定日時を過ぎたら自動非表示。空欄=無期限 |

4. **「保存」** ボタンで公開

### 6.3 お知らせの操作

| 操作 | アイコン | 動作 |
|---|---|---|
| 編集 | ✏️ 青 | 内容を変更 (公開状態を維持) |
| 公開/非公開トグル | 👁/👁‍🗨 黄→緑 | `is_active` を即切替 |
| 削除 | 🗑 赤 | 物理削除 (確認ダイアログあり) |

### 6.4 表示ロジック

- `is_active = true` かつ `(expires_at IS NULL OR expires_at > now())` のもののみ表示
- 複数該当する場合は `priority DESC, created_at DESC` 順
- 同じユーザーが「閉じる」ボタンで閉じても、次回ログインで再表示
- LocalStorage に "閉じた" 履歴を残してリピート抑制

### 6.5 タイプ別の使い分け推奨

| タイプ | 色 | 推奨用途 |
|---|---|---|
| ℹ️ お知らせ | 青 | 通常の情報提供 (メンテ予告等) |
| 🎁 キャンペーン | 緑 | 紹介キャンペーン・年末割引等 |
| 🚀 アップデート | 紫 | 新機能リリース告知 |
| ⚠️ 注意 | 黄/オレンジ | 障害情報・重要警告 |

## 7. 紹介者管理 (代理店・紹介報酬)

### 7.1 紹介者を発行する

1. **紹介者管理タブ** を開く
2. 右上の **「+ 紹介者を新規発行」** ボタン
3. モーダルで以下を入力:

| 項目 | 必須 | 説明 |
|---|---|---|
| 紹介者名 | ✅ | 代理店名・個人名 |
| 紹介者コード | 任意 | 空欄で自動生成 (英数字)。手入力時は半角大文字推奨 |
| メールアドレス | 任意 | 報酬振込先案内用 |
| 電話番号 | 任意 | 連絡用 |
| **報酬タイプ** | ✅ | %型 / 固定額型 |
| 報酬率/額 | ✅ | %の場合: 0〜100 / 固定額の場合: 円/件・月 |
| 備考 | 任意 | 契約条件等 |

### 7.2 報酬タイプの違い

| タイプ | 計算式 | 例 |
|---|---|---|
| **%型** | 月間売上 × % | Pro¥4,880 × 30% = ¥1,464/月 |
| **固定額型** | 件数 × 固定額 | 5件 × ¥1,000 = ¥5,000/月 |

### 7.3 紹介者コードの使われ方

- テナント発行モーダルの「紹介者コード」欄でサジェスト表示される
- 顧客が自分で入力することも可能
- テナント側の `referrer_code` フィールドに保存される

### 7.4 紹介者一覧

## 9. 事業収益ダッシュボード

### 9.1 基本KPI

| 指標 | 計算式 |
|---|---|
| **MRR** (月間定期収益) | アクティブテナント × プラン月額 (税別) の合計 |
| **ARR** (年間定期収益) | MRR × 12 |
| **有料契約数** | `license_status = 'active'` の件数 |
| **ARPU** | MRR ÷ 有料契約数 |

### 9.2 高度KPI

| 指標 | 計算式 |
|---|---|
| **月次解約率 (Churn)** | 直近30日の suspended数 ÷ 契約総数 |
| **直近30日 新規契約** | `created_at >= 30日前` の件数 |
| **継続率** | 1 - Churn |
| **LTV (見込)** | ARPU ÷ Churn率 |

### 9.3 紹介者別レポート

各紹介者の紐づくテナント数・月間売上・報酬額の集計表が表示されます。

## 11. トラブルシューティング

### 11.1 「ログインできない」

- マスターパスワード `rakushift1234` を試す (緊急復旧用)
- Supabase 側で `hq_admins` または `organizations` の状態確認
- ブラウザの DevTools コンソールで `auth_sessions` エラー有無

### 11.2 「テナント発行は成功したがメタ情報が保存されない」

- `update_tenant_metadata` RPC エラー → Supabase RPC ログで詳細確認
- 操作後の「⚠️ 警告トースト」をユーザーに表示しているので、その内容を確認

### 11.3 「本部から観覧しても店舗が表示されない」

- 本部の `scope_org_ids` が空 → 管轄編集ボタンで追加
- グローバル本部以外は明示的に scope 追加が必要

### 11.4 「お知らせが表示されない」

- `is_active = true` か確認
- `expires_at` が過去日時になっていないか確認
- ブラウザの LocalStorage に閉じた履歴が残っている可能性 → DevTools でクリア

### 11.5 「Stripe Webhook が届かない」

- `stripe_webhook_secret` が正しく設定されているか
- Stripe Dashboard の Webhook URL が `https://<railway-domain>/stripe/webhook` を指しているか
- Railway のログで `400` エラーの内容を確認

### 11.6 「キーを変更したのに反映されない」

- 最大5分のキャッシュあり
- Railway を強制再起動 (Railway Dashboard → Restart) で即時反映可

## 12. 付録: 用語と権限まとめ

### 12.1 用語

| 用語 | 意味 |
|---|---|
| **テナント** (店舗) | 1契約 = 1組織 = 1店舗。`organizations` テーブルの1行に相当 |
| **契約ID** | 15桁の数字。顧客が認識する唯一のID。`organizations.contract_id` |
| **organization_id** | UUID形式の内部ID。RLS で各テーブルを分離する基準 |
| **本部アカウント** | 複数テナントを観覧する管理層 (`hq_admins` テーブル) |
| **scope_org_ids** | 顧客本部が管轄する店舗のorganization_id配列 |
| **グローバル本部** | `is_global = true` の特権本部。全テナント自動管轄 |
| **as_hq モード** | URL `?as_hq=<contract_id>` で起動する本部観覧モード |
| **マスターパスワード** | `rakushift1234`。新規初期 + 緊急復旧用フォールバック |

### 12.2 権限階層

```
[運営マスター(admin)]
   ├─ プラットフォーム全機能アクセス
   └─ admin.html の全タブ操作可

[グローバル本部 (is_global=true)]
   ├─ 全テナント自動的に管轄
   └─ 個別店舗観覧可 (編集不可)

[顧客本部 (is_global=false)]
   ├─ scope_org_ids で指定した店舗のみ管轄
   └─ 個別店舗観覧可 (編集不可)

[店舗管理者 (各テナント)]
   ├─ 自テナントのみ閲覧・編集可
   └─ RLS で他テナントから完全分離

[店舗スタッフ]
   └─ 自分のシフト・希望休のみ操作可
```

## 13. シフト生成アルゴリズム簡素化 (v3.7.16〜v3.7.31)

観覧モードで顧客テナントを確認する際、以下の項目が **削除または変更** されている点に留意してください。サポート対応・障害切り分け時の参考情報です。

### 13.1 廃止された機能 (UIからも除去)

| 機能名 | 旧仕様 | 現状 |
|---|---|---|
| **NGペア** | スタッフ編集モーダルで同時出勤NGを指定 | 入力欄削除 |
| **管理者常駐数 (`min_manager`)** | 時間帯ごとに管理者最低数を指定 | 「社員 (月給+店長) 1名以上」に一本化 |
| **戦力バランス** | スキル平均値を時間帯で均等化 | 廃止 |
| **ピーク帯スキルミックス** | ピーク時に高スキル必須 | 廃止 |
| **疲労管理** | 連勤・連続深夜を抑制するスコア | 廃止 |
| **土日ローテ公平性** | 土日出勤を公平分散 | 廃止 |
| **時間帯分散** | スタッフ同士の時間帯重複を最小化 | 廃止 |

### 13.2 緩和された制約

- **週/月の最低出勤日数 (`min_days_week` / `min_days_month`)**: HARD制約 → **SOFT制約**。達成不能でも生成は通り、警告表示のみ。v3.7.29 で 200k → **30k** にさらに弱化 (希望事項扱い)。
- **承認済み出勤希望 (approved)**: HARD → SOFT 化 (v3.7.30。-10M ボーナスで通常時は確実に配置、過剰時 (20M) は諦め)。
- **OJT制約 (新人×メンター)**: 強制配置 → **軽い推奨**。
- **時給通常コスト**: 15k → **5k** (v3.7.29)

### 13.3 追加された機能

- **需給バランス警告バナー**: スタッフ管理画面最上部で「月需要 vs 全員 `min_days_month` 合計」を 3段階 (🟢適正 / 🟡やや過剰 / 🔴過剰) で可視化。顧客から「シフトが入らない」と問い合わせがあった場合、まずここを確認してください。
- **土日希望時間 自動補完**: 時給スタッフで土日希望時間が空欄の場合、保存時に平日希望時間を自動コピー (顧客作業負担削減)。
- **シフト時間の打ち込み入力**: ドロップダウンから `input type=time` に変更し、分単位で自由入力可。
- **過剰配置の絶対回避** (v3.7.28〜v3.7.31): 過剰配置率が 100% → **0%**。必要人数ぴったり配置になり、人件費過大の指摘が解消。
- **月給スタッフ優先 + 時給控え目 + スポット帯時給投入** (v3.7.28): 月給スタッフ不在 30k / 時給通常 5k / time_staff_req≥2 スポット帯はコスト 0

### 13.4 v3.7.28〜v3.7.31 過剰絶対回避ポリシー

| バージョン | 変更内容 |
|---|---|
| v3.7.28 | COVERAGE_OVER_DAY 5M→**20M** / COVERAGE_OVER_SLOT 4M→**20M** / 月給スタッフ不在 30k 復活 / 時給通常コスト 15k 追加 / スポット帯時給投入 0 コスト |
| v3.7.29 | min_days SOFT 200k → **30k** / 時給通常コスト 15k → **5k** (希望シフトを通すため) |
| v3.7.30 | 承認済み希望 HARD → SOFT 化 (配置時 -10M ボーナス、過剰時諦め) |
| v3.7.31 | Greedy フォールバック過剰回避厳格化 (`>=` でぴったり停止) |

**本番想定 10名/28日 のテスト結果**: ぴったり配置 71%→**100%** / 過剰 8/28→**0/28** / 希望充足 50%→66.7% / 求解時間 5.2s→1.8s

### 13.6 サポート対応時の注意

- 旧バージョンで設定された NGペア・`min_manager` データはDB上に残存している可能性があるが、現行アルゴリズムでは読み込まれない。
- 「週/月の最低出勤日数が満たせない」という顧客問い合わせは v3.7.16 以前は生成エラーだったが、現行はSOFT化のため警告に変わっている。
- 「承認済み希望なのに配置されていない」という顧客問い合わせは v3.7.30 以降の正常挙動 (過剰回避優先)。スタッフ管理画面の **需給バランス警告バナー** で過剰登録を確認するよう案内。
- 配置理由バッジから「戦力バランス」「ピーク帯スキル」等の文言は除去済み。残っている場合はキャッシュクリア (Ctrl+Shift+R) を案内。
